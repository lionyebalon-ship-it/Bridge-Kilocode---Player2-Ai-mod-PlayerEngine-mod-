# NPC Characters — guide

Player2NPC companions are driven by a small character roster served by the
bridge. Each companion has its own personality, and in-game you pick which one
appears (the H menu). Each character can also use **its own model, temperature
and max_tokens** — "many brains, many faces". The global model in
`bridge/config.json` remains the default for anything a character does not
override.

## The roster file: `bridge/characters.json`

```json
{
  "characters": [
    {
      "id": "kilo",
      "name": "Kilo",
      "short_name": "KILO",
      "greeting": "Hey there! I'm your companion on this server. What are we up to today?",
      "description": "You are a helpful, concise Minecraft companion AI agent.",
      "voice_ids": [],
      "meta": { "skin_url": "" },
      "model": "nvidia/nemotron-3.5-lightning:free",
      "temperature": 0.9,
      "max_tokens": 4096
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `id` | **Required by the mod.** Persists the companion's state. Auto-generated by the CLI (slug of the short name, e.g. `bob`) and backfilled by the bridge at serve time when missing. Keep ids stable — renaming an id orphans the companion's stored state. Collisions get `-2`, `-3`, … suffixes. |
| `name` | Display name shown in menus. Also the handle the bridge uses to decide which character a chat call belongs to. |
| `short_name` | The by-name chat gate: your in-game message must contain this name (or the name) for the companion to answer. |
| `greeting` | Sent by the NPC on spawn. Also used to classify the first message as a greeting rather than a generic event. |
| `description` | Feeds the NPC's system prompt — this is where the personality actually lives. |
| `voice_ids` | Voice IDs for TTS (stubbed in the bridge; leave `[]`). |
| `meta.skin_url` | Optional skin texture URL. |

## Per-character model overrides

Three optional keys let a character run a different brain than the rest of the
server. All of them default to the global values in `bridge/config.json`.

| Key | Type | Default | Meaning |
|---|---|---|---|
| `model` | string | global `model` | Any id listed by `python3 bridge/run.py --check`. |
| `temperature` | float `0.0`–`2.0` | global `temperature` | |
| `max_tokens` | int `> 0` | global `max_tokens` | Clamped against the target model's own context window and completion cap. |

There is deliberately **no** `model_context_limit` key — the bridge reads the
window from the gateway catalog, because a hand-entered value that does not match
the model would silently truncate replies.

Rules worth knowing:

- **The overrides live in `bridge/characters.json`.** A `characters` array in
  `bridge/config.json` is only a *fallback* used when the roster file is absent,
  so per-character keys placed there are silently ignored. The bridge logs a
  WARNING at startup when this happens (character id plus the ignored values).
- A model that has left the catalog makes **that character** fall back to the
  global model, with one WARNING at startup. The rest of the roster is unaffected
  and the bridge never refuses to start.
- Malformed values are dropped rather than fatal: a mistyped `temperature` means
  that character simply uses the global one.
- Temperature is omitted from the request (not merely ignored) for any model the
  catalog says does not support it.

**Attribution is best-effort.** The bridge decides which character a call belongs
to by reading `Your character's name is <name>.` out of the system prompt, so a
call the mod sends *without* that line is attributed to no one (`char=-` in the
logs) and uses the global model even in a multi-character roster. Observed with
bare-text command-feedback calls. It degrades to the previous single-model
behaviour rather than failing, but it means a second character's overrides do not
always apply to 100% of its calls.

Model choice is visible per call in the bridge log and in
`GET /bridge/stats` → `recent_requests[]` (`kind`, `character_id`, `model`).


## Managing the roster (CLI)

```bash
python3 bridge/characters.py list
python3 bridge/characters.py add --name "Bob the Miner" --short "BOB" \
  --greeting "Hey there, name's Bob." --description "A gruff but friendly miner."
python3 bridge/characters.py show --name "Bob the Miner"
python3 bridge/characters.py remove --name "Bob the Miner"
```

- `add` requires `--name`, `--short`, `--greeting`, `--description`.
- Optional `--id` pins the id (validated: `^[A-Za-z0-9_-]+$`, ≤64 chars);
  without it the id is the slug of `--short` (e.g. `bob`). `--force` allows
  overriding an existing id.
- `remove` matches on `name` OR `short_name`.
- `--path` points the CLI at a different roster file (used by tests).

## Hot reload

The bridge reads the roster on every `/v1/selected_characters` call and reloads
it automatically when the file's mtime changes — **no bridge restart needed**.
Edit `characters.json` by hand or via the CLI, then reopen the in-game H menu
to see the new cast.

## Troubleshooting

- **NPC won't spawn / "Persisted companion state was unavailable or rejected"** —
  the character has no `id`. The mod aborts spawning for id-less characters.
  Add one with `--id` or delete the field and let the bridge backfill it on the
  next serve (check `curl -s http://127.0.0.1:9800/v1/selected_characters`).
- **H menu shows no characters** — check the roster is being served:
  `curl -s http://127.0.0.1:9800/v1/selected_characters`, and confirm
  `bridge/characters.json` is valid JSON with a non-empty `characters` array.
- **The NPC ignores you in chat** — your message must contain the companion
  name (the by-name gate): e.g. start with "Kilo, …".
- **My character's `model` in `bridge/config.json` has no effect** —
  `bridge/characters.json` is served instead and wins. Move the override into
  the roster file. The startup WARNING names the character and the ignored value.
- **The NPC answers with the global model, not the one I set** — either the model
  is no longer in the gateway catalog (check with
  `python3 bridge/run.py --check`, which reports a MISSING line per roster model),
  or the mod sent that call without a system prompt naming the character (see
  "Attribution is best-effort" above; the log line shows `char=-`).
